# Building a native Mac display utility

MacMonitorControl’s first release should make everyday display changes quick and reversible. Start with a native menu bar app that identifies each screen, offers the modes macOS exposes, and adjusts brightness and other hardware values where the connection supports them. Saved desk setups are the strongest next feature because they combine layout, modes and monitor settings into one action. BetterDisplay Pro also sets a benchmark for flexible HiDPI, virtual desktops, streaming and advanced color, each of which needs a separate feasibility check. The comparison below reflects vendor and Apple documentation reviewed on November 23, 2026. The release phases are proposals for MacMonitorControl. ## Native APIs cover the common path and leave hardware questions open

A proposed implementation uses **SwiftUI and AppKit for the native shell** and **Core Graphics for display enumeration, change notifications, existing modes, origins and mirroring**. Quartz configuration transactions can group layout changes. Use a short confirmation timer and store a recoverable prior configuration for mode changes. Compare logical and backing pixel sizes so the user can distinguish scaling options. AppKit, ServiceManagement and ColorSync cover portions of the shell, login-item and ICC workflows. [SwiftUI MenuBarExtra](https://developer.apple.com/documentation/swiftui/menubarextra) · [Quartz Display Services](https://developer.apple.com/documentation/CoreGraphics/quartz-display-services) · [Quartz transactions](https://developer.apple.com/library/archive/documentation/GraphicsImaging/Conceptual/QuartzDisplayServicesConceptual/Articles/DisplayTransactions.html) · [ServiceManagement](https://developer.apple.com/documentation/servicemanagement/smappservice) · [ColorSync](https://developer.apple.com/documentation/colorsync/colorsyncdevicesetcustomprofiles%28_%3A_%3A_%3A%29?language=objc) · [Apple’s mode recovery guidance](https://support.apple.com/en-us/guide/mac-help/mchl86d72b76/mac)

Keep device commands separate from Core Graphics settings. **DDC/CI capability depends on the specific command, monitor, firmware and connection**, including adapters, docks and KVMs. Brightness can work with missing readback or unsupported input commands. Treat software overlay dimming, hardware backlight, standby and actual desktop disconnect as four different operations. Likewise, check whether Core Audio output volume is writable separately from DDC speaker volume. Keep DisplayLink driver support separate from direct DDC and test it independently. [BetterDisplay DDC](https://betterdisplay.pro/guide/interface-reference/settings/displays/display/device-control/ddc/) · [Core Audio properties](https://developer.apple.com/documentation/coreaudio/audiohardwareobject) · [Synaptics brightness and contrast support](https://support.displaylink.com/knowledgebase/articles/2021015-brightness-and-contrast-control-settings)

**Hardware writes, arbitrary modes, virtual desktop creation, true disconnect and system-wide HDR/XDR changes require prototypes.** Open-source projects document private APIs for Apple silicon DDC, Apple display brightness, host virtual desktops and true disconnect. Physical flexible scaling can use system overrides and require authorization or reactivation. ScreenCaptureKit is a public path for capturing an existing screen, app or window with the appropriate permission. Prove the specific hotkey implementation before determining its Accessibility or Input Monitoring requirements. Keep capture permissions tied to optional capture features. [BrightSync implementation](https://github.com/pszypowicz/brightsync) · [BetterDisplay system configuration](https://betterdisplay.pro/guide/interface-reference/settings/displays/display/system-configuration/) · [Lunar FAQ](https://lunar.fyi/faq) · [DeskPad source](https://github.com/Stengo/DeskPad/blob/main/DeskPad/Frontend/Screen/ScreenViewController.swift) · [ScreenCaptureKit sample](https://developer.apple.com/documentation/screencapturekit/capturing-screen-content-in-macos) · [Apple Input Monitoring](https://support.apple.com/en-bn/guide/mac-help/mchl4cedafb6/mac)

For profiles, use display identity data and connection context together. A display name alone is insufficient, and two identical monitors can still be ambiguous. Ask the user to identify screens when a preset would otherwise guess. Track support and current state per command, preserve healthy controls after failures, and keep diagnostics local with serials redacted from shareable logs. [Apple ApplicationServices functions](https://developer.apple.com/documentation/applicationservices/applicationservices_functions) · [Lunar FAQ](https://lunar.fyi/faq) · [displayplacer README](https://github.com/jakehilborn/displayplacer#readme)

## Release decisions depend on hardware and distribution tests

**Validate two display paths first** using a MacBook built-in panel and a known DDC-capable monitor on direct USB-C/DisplayPort. Extend the matrix to direct HDMI, a dock or KVM, a pair of identical monitors, an HDR/high-refresh panel and a DisplayLink dock. Add Intel, Apple external displays and AirPlay/Sidecar where the project plans to support them. Record the Mac/chip, macOS build, display firmware, link, operation and readback result. Test disconnect/reconnect, wake, clamshell, changed input, permission denial, app quit and stale modes. Protect the last usable display and test timed rollback and keyboard escape before offering risky topology changes. Use a simulated backend for preset matching, mode selection and rollback tests. Verify DDC and visual behavior on physical hardware. [Apple display connectivity](https://support.apple.com/en-us/102501) · [BetterDisplay dock guide](https://betterdisplay.pro/guide/tutorials/hardware-brightness-and-volume-through-dock/) · [BetterDisplay connection safety](https://betterdisplay.pro/guide/interface-reference/app-menu/device-menu/header-and-connection/)

The project still needs decisions on the minimum macOS version, Intel support, launch hardware and distribution channel. A Mac App Store build must satisfy sandbox and public-API requirements. Direct distribution uses Developer ID and notarization. Decide whether the project may depend on undocumented APIs before making hardware or Pro-style capabilities core release promises. Verify the chosen design in a signed build under the intended distribution constraints. [App Store Review Guidelines](https://developer.apple.com/app-store/review/guidelines/) · [Developer ID](https://developer.apple.com/developer-id/) · [Apple notarization](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution/)

The comparison is documentation-based. Local monitor compatibility, signed-build behavior and App Store review remain unverified.
